# Agent Note: JPX AJAX 换轮清除定时器后的扫描恢复

Status: implemented

## Problem

JPX 开启 `AjaxRound` 时，将解析后的验证码 body 导入浮层，并通过原生表单 submit 事件发送 AJAX 请求。换回战斗页时，它会批量清除最近 100 个页面定时器。如果扫描防抖定时器仍未执行，核心 App 的待扫描句柄不会归零；后续验证码出现时，旧逻辑看到非空句柄直接返回，导致只答第一题，直到刷新页面。

本地 Chromium 扩展 fixture 在修复前完成第一题，但等待第二题提交超时；核心单元回归同样只收到一次处理调用。

## Decision

每次验证码相关 mutation 都重新挂载扫描定时器。首次排队记录 `performance.now()` 加扫描间隔的截止时间；后续重挂只等待剩余时间，已过期则立即排队。不再将非空句柄视为底层定时器仍存在的证明，也不让频繁 DOM 变化不断延长等待。

目标变化仍先取消旧轮次，再调度扫描。目标去重、失败冷却、控件身份检查与原生提交流程保持不变；无关 mutation 不唤醒扫描，销毁仍取消待扫描任务。修复位于共用核心，用户脚本与扩展共用，不改 JPX、浏览器权限或跨上下文协议。

### 既有决定检索

检索活跃 lifecycle 的 JPX、扫描、防抖、定时器与局部切页：[验证码恢复](2026-09-22-captcha-recovery-and-manual-selection.md)解决观察节点替换，[主动取消](2026-10-02-audit-regressions.md)解决旧任务阻塞，均保留。本篇补外部清除扫描定时器后的恢复，不翻转原取消/防抖理由；无须吸收或废弃的相关 proposed/rejected 记录。

## Alternatives considered

- 修改 JPX，只清理其自己的定时器：根因边界最清晰，但需要用户替换第三方脚本，也不能覆盖其他脚本的同类行为；本次只读参考文件，不修改。
- 每次 mutation 重新等待完整 100ms：代码更短，能恢复清除的定时器，但持续变化会让扫描饥饿；保留原截止时间。
- 移除防抖，或增加固定轮询：前者不再受页面 timer sweep 影响，后者能在没有新 mutation 时恢复；但分别增加扫描频率或常驻工作，超出当前问题所需范围。
- 监听 JPX 合成的 `DOMContentLoaded` 并重新初始化 App：能捕捉该脚本的换轮通知，但重复初始化会干扰未完成任务与已有状态；继续使用通用 DOM 观察，不引入脚本专属生命周期。

## Consequences

每次相关 mutation 多一次清理/重挂，同时最多一个定时器，原防抖窗不延长。恢复依赖后续相关 mutation，无后续变化时不轮询、不恢复；此机制不全面保护模型请求、点击延迟或任意第三方清理。

单元回归覆盖首题后清除定时器、下一题处理、同目标去重、连续 mutation 下原截止时间和销毁。Chromium content E2E 在真实扩展隔离上下文中，模拟页面导入、原生 submit、页面侧清除最近 100 个 timer ID 与合成 `DOMContentLoaded`，连续三题逐题核对一次检测、一次提交和一条成功历史，全程不刷新。

上述浏览器回归使用受控 fixture Host，不运行完整 JPX 战斗逻辑，不访问生产模型服务，也不证明 Firefox、真实游戏或受保护模型鉴权。
